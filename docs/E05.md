# E05：自动发现与配对

2026-09-30：发现、首次信任、平台凭证、认证与撤销功能已接入 Sender/Hub。追加的逐项检查及 Windows/Linux 代码就位证据见 [完整性检查](E05-AUDIT.md)。共享 Rust 核心与三端凭证后端已实现，本轮只执行 macOS 验证。桌面发现/邀请界面由 E07 接入这些接口。

## 使用

全部命令经项目内开发环境运行。正式 serve 默认监听 `0.0.0.0:7443`，旧实验资料默认 loopback；可显式 `--listen` 覆盖。正式入口使用 profile 相邻文件凭证；`init` 是保留的明文实验入口。

```sh
# 在 Hub 上选择一个真实可用的输出 UID。setup 目录需为空。
tools/dev target/release/neonmix-hub setup \
  --directory .local/my-hub --output 'coreaudio:YOUR_OUTPUT_UID' --name '客厅'
tools/dev target/release/neonmix-hub serve \
  --config .local/my-hub/server.json --listen 0.0.0.0:7443

# 另一个终端/设备浏览候选。输出 resolved/removed 事件，trusted=false。
tools/dev target/release/neonmix-hub discover --seconds 5

# Hub 管理员开启一次性邀请；默认自动发现自己的 Hub。
tools/dev target/release/neonmix-hub invite \
  --credential .local/my-hub/admin.json --out .local/living-room.invite.json

# 将邀请文件从 Hub 管理员交给 Sender 后，在 Sender 上运行。
tools/dev target/release/neonmix-hub pair \
  --invite .local/living-room.invite.json --credential .local/living-room.sender.json \
  --name '书房电脑'

# 已配对资料默认重新发现地址并验证身份，无需保存 IP。
tools/dev target/release/neonmix-hub snapshot --credential .local/living-room.sender.json
tools/dev target/release/neonmix-hub watch --credential .local/living-room.sender.json --seconds 30
# 显式发送测试信号；实际应用音频可使用 E06 的 --virtual-output/--output-binding。
tools/dev target/release/neonmix-hub send --credential .local/living-room.sender.json --seconds 10
```

macOS 的元数据和邀请文件留在上述项目路径；实际私钥/长期令牌以明文 JSON 存于 profile 父目录的 .credentials，Unix 0700/0600，Windows 当前用户受保护 DACL。开发缓存和编译产物仍位于 `.local/`、`target/`、`artifacts/`。正式 `setup` 不预先登记两个实验 Sender。

`invite --seconds 120` 的范围是 1–300；邀请秘密不输出到终端。凭证只在取得可信邀请、完成固定证书/UUID 校验之后生效。成功配对不发声；只有用户主动调用 `send` 建立媒体会话。保留邀请文件可用于一次失败后的原请求恢复；完成后可删除它。

取消邀请：

```sh
tools/dev target/release/neonmix-hub cancel-invite \
  --credential .local/my-hub/admin.json --invitation-id '<invitation-uuid>'
# 删除本地长期令牌和资料；支持清理未完成配对的 pending 资料。
tools/dev target/release/neonmix-hub forget --credential .local/living-room.sender.json
```

高级诊断可在 `pair`、`send`、`snapshot`、`watch`、`control`、`diagnostics`、`invite` 和 `output add` 指定 `--hub https://<address>:<port>`；仍验证固定身份。旧实验凭证的省略地址行为保持 `https://localhost:7443`。证书变化时用新邀请和新资料路径显式配对；旧资料不会被未知密钥自动替换。

管理员撤销与重新允许继续使用 E04 的 `control --command <file>`。例如先取管理员 snapshot 的 `revision`，用新的 `request_id` 提交：

```json
{"request_id":"<new-uuid>","expected_revision":5,"operation":{"type":"revoke","device_id":"<paired-device-uuid>"}}
```

撤销立即关闭该身份的活动媒体/WSS，旧令牌之后均拒绝。`disconnect` 停止活动会话并禁止再播；`allow_playback` 重新允许，但不会自动发起发送。配对成功结果和凭证元数据均提供 `device_id`。

## API 和失败规则

所有端点都在 TLS 1.3 上；请求体上限 16 KiB。E04 既有 API 不变。

| 方法/路径 | 权限 | 内容 |
|---|---|---|
| GET `/v1/identity` | 不要求令牌，客户端必须验证固定证书 | 公开 version、Hub UUID、room_name |
| GET `/v1/me` | 已认证设备 | 自己的 device_id 和 Hub UUID |
| POST `/v1/pairing/invitations` | Admin | `{ttl_seconds}` → 完整一次性邀请；不允许自报角色 |
| POST `/v1/pairing/cancel` | Admin | `{invitation_id}`；取消可重复，无需公开邀请秘密 |
| POST `/v1/pairing/complete` | Bearer 一次性秘密 | `{invitation_id,request_id,name,token_sha256}` → `{hub_id,device_id,revision}` |

领取仅固定授予 Member。失败码为 `pairing_unauthorized_or_expired`（401）、`pairing_already_used`（409）、`pairing_invalid_argument`（400）、`pairing_quota_exceeded`（429）；管理员权限、持久化失败、角色校验沿用 E04 错误。邀请和领取结构拒绝额外字段。服务端不传回或持久化长期令牌明文。

Windows 邀请及资料文件使用显式的仅所有者 DACL，要求文件系统支持持久 ACL；Unix 使用 0600。新文件排他创建，状态及资料使用随机私有临时文件原子替换。

元数据未完成时，普通 Sender/控制入口拒绝使用；重跑相同 `pair` 先验证已有令牌，能恢复“服务端已落盘但本地尚未完成”的结果。凭证库不可用时保留可解释的失败，不用文件令牌回退。取消/失效邀请后的 pending 条目可显式 `forget`。
