# ADR-013：隔离的 AirPlay Speaker 音频接入

2026-10-01；状态：实验实现，正式引擎与跨平台分发仍待 AP00/AP08 验证。依据专项设计/计划与 ADR-008、ADR-012。

固定 UxPlay 1.73.7 的协议音频源码，自己构建 `neonmix-airplay-worker`，不使用 UxPlay 应用入口和 renderers。最小 C/C++ 桥负责解密、协议 PIN/公钥认证、时间映射、音频解码；Rust Hub 持有发现、准入、生命周期、受限控制、定时接入、Mixer 与实体声卡。worker 的 GPL 标注与固定源码/补丁独立记录，不变更 Rust workspace 许可；正式组合与分发条件未通过前不标记可发布。

协议必须在发现与握手同时限定纯音频，移除实际视频接收路径；未知或视频类型在创建媒体资源前拒绝。经典 NTP/UDP profile 仅声明当前实现的格式与能力，不复制 Apple TV 全部能力。原版 `-vs 0` 或屏幕镜像成功不构成本决策的验收证据。

第一实现用匿名 stdin/stdout 控制管道与高熵能力令牌保护的 loopback PCM 通道，固定 LE 帧、有界长度和单 worker owner。这样可先验证 C/Rust 的格式、授权与时序接缝。它是计划中当前用户 Unix socket/Windows NamedPipe 的明确实施差异，不能据此宣布三端权限与安装已通过。

`AudioBlock` 增加可选呈现目标；None 保留原生通道语义。AirPlay 在非实时层持有有界长提前量，Mixer 定时通道按实际输出呈现锚点逐采样消费，避免额外加原生 70 ms。声卡输出 nominal resampler 以真实输入/输出坐标传递锚点，不再次加已经由 rubato phase 补偿的 delay。协议 PTS 决定外部来源相对设备的消费位置，原生漂移控制继续独立运行。

AirPlay 管理状态与原生设备/会话隔离，复用现有 TLS/Admin 验证；来源仅有音频授权，没有房间控制凭证。开始接收与媒体开始的两个阶段都检查代际及配额；撤销/停止先关媒体门和 Mixer lane，再关协议会话。独立停止标志与受控子进程回收避免控制消费者堵塞时拖住 Hub 退出。

当前 macOS 原型不能代表 iPhone/iPad/Mac 全场景兼容，更不能代表 Windows/Linux 发布完成。必须继续取得原生选择器、正确 PIN/已配对重连、实际音频及源端视频伴音的证据，再决定正式默认引擎和支持范围。

2026-10-02 修订：按用户明确选择，默认采用低延迟音乐播放。Hub ingress 在每个 epoch 固定平移来源 PTS，首包保留最多 120ms 接收后余量，后续保持连续时间线；原有按声卡锚点消费与 sinc SRC 保持。可选 synchronized 保留完整来源 PTS，切换要求先断开。此选择有明确的声音提前于源视频的后果，不将源端预缓冲叫作 Hub 处理耗时。设备页可合并展示公开 AirPlay 来源摘要，但不把它写入原生身份/权限成员表。

2026-10-03 平台复测修正：120ms 余量以提交设备为基准，首包 PTS 平移时额外计入设备 `playback−callback` 积压。此前 Ubuntu 的约106.6ms积压与1024帧回调已消耗接收余量，macOS确定性 Ingress→Mixer 回归重现跳采样；修正保留短队列容量与同epoch固定PTS平移，不因逐包到达或设备积压变化重定时。
