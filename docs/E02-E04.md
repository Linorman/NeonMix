# E02–E04 使用与验收

本轮实现可独立运行的 Sender/Hub、安全媒体适配、实时 Mixer 和权威控制 API。macOS 通过 `tools/dev` 构建，GStreamer、缓存、临时身份及编译产物均在项目内。接口和容量以 [合约](MEDIA-CONTROL-CONTRACT.md) 为准。

## 本机启动

```sh
tools/dev python3 tools/prepare_gstreamer.py
tools/dev cargo build --workspace --release --locked
tools/dev target/release/neonmix-audio devices

# 选择已枚举的稳定输出 ID。此例用于数字读回，不改变系统默认路由。
tools/dev target/release/neonmix-hub init --output coreaudio:BlackHole2ch_UID
tools/dev target/release/neonmix-hub serve --config .local/hub-lab/server.json
```

另外两个终端分别运行两路输入：

```sh
tools/dev target/release/neonmix-hub send --credential .local/hub-lab/sender-a.json --seconds 60 --frequency 437
tools/dev target/release/neonmix-hub send --credential .local/hub-lab/sender-b.json --seconds 60 --frequency 659
tools/dev target/release/neonmix-hub snapshot --credential .local/hub-lab/admin.json
tools/dev target/release/neonmix-hub watch --credential .local/hub-lab/admin.json --seconds 60
tools/dev target/release/neonmix-hub diagnostics --credential .local/hub-lab/admin.json
```

使用真实虚拟输入时给 Sender 添加 `--capture 'coreaudio:BlackHole2ch_UID'`。同机测试应将 Hub 绑定到另一个输出 UID，以免把房间输出重新采集回自身；虚拟输入需要宿主已有麦克风权限。采集采用设备实际 44.1/48/96 kHz 格式并转内部 48 kHz stereo；采集时间线/格式变化会停止该次发送，需要建立新会话，不能接着使用旧媒体上下文。

## 局域网与控制

```sh
# 在 Hub 上：地址必须是证书中的 SAN；可多次提供 --host。
tools/dev target/release/neonmix-hub init --directory .local/lan-room \
  --output '<stable-output-id>' --host '<hub-lan-ip-or-dns-name>'
tools/dev target/release/neonmix-hub serve --config .local/lan-room/server.json --listen 0.0.0.0:7443

# 在 Sender 上，用事先明确提供的对应实验凭证，不通过发现结果自动建立信任。
tools/dev target/release/neonmix-hub send --credential .local/sender-a.json \
  --hub 'https://<hub-lan-ip-or-dns-name>:7443' --capture '<capture-id>' --seconds 60
```

IPv6 可使用 `--listen '[::]:7443'` 和证书中配置的 IPv6 地址/DNS 名。成员凭证只管理自己的输入，admin 凭证用于房间和设备管理。读取 snapshot 后把合约中的命令 envelope 保存到项目 `.local/command.json`，用 `control --credential ... --command .local/command.json` 提交。成功值取服务端 receipt/snapshot；409 时重新取快照，不显示尚未提交的值。

## macOS 检查入口

```sh
tools/dev python3 tools/check.py
tools/dev python3 tools/e02_e04_probe.py --device coreaudio:BlackHole2ch_UID --soak-seconds 30
tools/dev python3 tools/e02_e04_probe.py --device coreaudio:BlackHole2ch_UID --ipv6
tools/dev python3 tools/capture_sender_probe.py \
  --capture coreaudio:BlackHole2ch_UID --output '<another-explicit-output-id>'
tools/dev python3 tools/e02_e04_completion_probe.py --device coreaudio:BlackHole2ch_UID
tools/dev python3 tools/hub_soak_probe.py --device coreaudio:BlackHole2ch_UID --seconds 3600
```

`check.py` 执行 fmt、Clippy、workspace 测试、release、原生插件探针、双路传输、丢包/重放、错误指纹和实际 sinc 的四组 600 秒漂移注入。Native security 测试覆盖真实序号/时间戳回绕、认证失败/损坏、SRTP/SRTCP 重放、新密钥隔离、期限、乱序与迟到，并查看实际 PLC 样本。

BlackHole 控制探针验证真实数字读回、两路混音、输入 Mute、多 Solo、总控、拒绝越权、幂等/版本冲突、WSS 增量与重启后的撤销。Capture 探针用不同的输入/输出设备验证三档原生采集转换与 SRTP。脚本删除临时凭证，不保存 PCM。原始日志在 `artifacts/`，选取的报告在 `docs/evidence/e02-e04/`。

故障探针额外显式填满 B 的 stdout 管道；管道堵住时要求 B 的 PCM 持续推进且无欠载增加，解堵后必须读到 `diagnostic_drops > 0`，避免没有产生实际背压的假阳性。

故障探针按阶段保留基线：输出格式故障/重开允许中断该输出；随后 A 路断网时，B 路的欠载增量必须为 0，并数字读回 659 Hz。稳定性探针在预热和最终收尾都要求欠载、PCM 时间线缺口、队列丢弃及回调超预算为 0，同时检查实际数字输出静音比例和 Sender 是否跳过源时间。

补充故障探针验证真实 UDP 反馈驱动编码器降级和恢复、慢控制不阻塞媒体、客户端快照/WSS 重订阅、真实落盘失败、单路故障隔离及 Hub 同 UID 44.1 kHz 重开。此前双路联跑曾提前失败；本轮通过分阶段墙钟/CPU 观测定位等待停顿，修正事件唤醒与实际普通线程优先级后，完整 30 分钟数字读回通过。结果和资源数据见[稳定性记录](E02-E04-STABILITY-20260930.md)，完整边界见[完成度核对](E02-E04-AUDIT.md)。完整计划的跨机、8/24 小时及模拟端延迟仍需单独验证。

此范围不等同于三端 G2、成品驱动、完整 E05 发现配对、桌面产品或 v1 发布。跨机实体端到端延迟、三端互通与长期硬件稳定性仍按开发计划在后续条件具备时验收。

本轮用户指定以持续一小时作为开发验收，当前修订制品已通过；原始运行没有中途改参数或换二进制。实际证据与正式长期验收边界见[逐项核对](E02-E04-REQUIREMENTS.md)。
