# E02–E04 故障与验证复核（2026-09-30）

本文件为早先复核的历史记录；后续已完成调度修正与 30 分钟通过复验，最新状态见[稳定性记录](E02-E04-STABILITY-20260930.md)。

当时结论：主要功能已有实现和分项证据，但没有一次通过的 30 分钟双路记录支持稳定性完成。虚拟机、普通线程调度、GStreamer 内部等待和其他宿主活动均不能凭现有记录单独定为根因。本次先修复构建状态与证据采集，不继续扩大缓冲或提升到未经测量的实时调度等级。

## 发现与处理

1. **根因归属缺少证据。** `max_loop_gap_ns` 是两次循环入口间的墙钟时间，`max_source_backlog_ns` 是逻辑源期限差；两者不能区分 CPU 调度、锁等待、编码调用耗时或进程暂停。周期日志在故障前一秒，不能用此前约 15 ms 的最大值解释之后约 100 ms 的故障。新增 `sender_failure` 保存故障时入口间隔、当前循环耗时、循环入口积压和 `push_frames` 耗时。根因仍待此证据定位。

2. **临时 Mach 实时策略未达到可采用条件。** 中断时 `DeadlineGuard` 仍有三个 Clippy 错误；1 ms 计算/2 ms 期限参数没有 CPU 执行时间或降级统计依据。其覆盖的媒体代码存在分配、GStreamer 调用及 Mutex；公有 guard 还可以跨线程移动，析构却作用于当前线程。已删除该 guard 和生产调用点，保留已验证的普通 QoS 配置。没有把补齐注释当作完成实时安全验证。

3. **“receiver count changed” 是结果，不是原始故障。** Sender 源期限超限时主动关闭上下文，Hub 的接收数减少是后果。旧探针又先关闭 Hub，可能使 Sender 追加清理引发的 `Connection refused`。已改为清理前保存诊断、进程状态、Sender 最后统计及 stderr，清理顺序改为采集/Sender 在前、Hub 在后。

4. **测试制品与并发隔离不足。** 旧工具只记录 Hub 的启动哈希，所有进程直接从可被后续构建替换的 `target/release` 启动，未记录音频 CLI 哈希。已为每轮复制固定的两个二进制并记录各自哈希，增加同一 soak 工具的互斥锁。历史记录不能据此倒推发生过并发构建干扰；也不能排除未记录的外部负载。其他工具/人工设备操作不受此锁约束。

5. **失败证据与清理不够可靠。** 原采样间隔 30 秒，子进程提前退出只能等下一次诊断；原 `finally` 中设备采样率恢复异常会阻止凭证目录清理及结果落盘。已增加循环中的子进程退出检测，并独立处理恢复/清理错误，失败时仍写结果。

6. **功能测试通过不能覆盖长期稳定性。** 70 ms 余量对受控 60 ms 交付停顿有反事实回归证据（旧配置失败、新配置通过），仅证明这一个边界。真实长跑仍失败，实际端到端延迟也没有测量，不能宣称增加 10 ms 余量已经解决问题。现保留有限的 70 ms 配置及其容量上限，停止继续盲目增加。

## 当前验证边界

删除 Mach 实时升级后，`neonmix-media`/`neonmix-hub` 的 Clippy、10 项协议/安全/事务测试和 release 构建通过。修订探针的[60 秒正常双路](../artifacts/hub-soak/20260930-125910/result.json)通过，同工具并发启动被互斥锁拒绝；[受控暂停故障](evidence/e02-e04/review-failure-harness-20260930.json)保留了约 210 ms 循环入口间隔和约 58 μs 送编码器耗时，清理无错误。该故障是主动注入，仅验证观测能力，不解释历史根因。短测不替代 30 分钟、更不替代 8/24 小时或跨机验收。历史“63 项测试通过”属于对应历史检查记录，不作为之后所有未验证修改的背书。

后续应使用固定制品、逐阶段耗时、线程 CPU 时间或系统调度跟踪定位一次真实长停顿，再针对该阻塞点修改并复验。现有材料不足以要求用户继续关闭其他程序，更不足以证明需要硬性实时线程策略。
