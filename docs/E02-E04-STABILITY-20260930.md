# E02–E04：长期运行停顿修复（2026-09-30）

E02 的安全媒体与反馈、E03 的 Mixer/时钟补偿和 E04 的权威控制已有实现。本轮优先处理真实双路中出现的停顿与退出；只在 macOS 测试，没有使用子 Agent。**macOS 功能回归与完整 30 分钟双路复验通过。** 这解决了本机已复现的短时间长跑失败回归；不据此宣称跨机或 8/24 小时已验收。

## 故障证据

| 条件 | 实际结果 | 可据此得出的结论 |
|---|---|---|
| 原等待方式，加入分阶段墙钟/CPU 观测 | 约 480 秒时，两路的 1 ms 等待分别耗时 122.915/123.070 ms；CPU 仅 24.5/22.5 μs，之后送编码器约 36 μs；源积压超限退出 | 此次直接触发点在等待/调度，不是编码计算耗尽预算；不能区分内核计时合并与可运行后的调度延迟 |
| 改为事件唤醒 + critical timer，保持原 QoS | 约 118 秒后额外等待约 53 ms；A 路出现 480 帧欠载，丢包、PCM 缺口和队列丢弃均为 0 | 单换等待原语不足以修复 |
| 调度独立读回 | QoS 请求成功、requested class=33，但实际 base priority=31；普通 `SCHED_OTHER` 请求 47 后读回 policy=1/base=47 | 旧 `qos_active=true` 不能证明实际优先级已生效 |

原始故障见 [等待停顿](evidence/e02-e04/wakeup-failure-20260930.json) 和 [仅修改等待方式的失败](evidence/e02-e04/event-wakeup-failure-20260930.json)。前一轮包含受控计算负载、一次采样和后期编译，条件写在报告中；后一轮没有受控负载或采样器。不能把两轮均描述为空闲环境。

Apple XNU 对未声明应用角色的进程设置 QoS ceiling，本机请求值与实际值的差异与该实现一致，见 [task_policy.c](https://github.com/apple-oss-distributions/xnu/blob/main/osfmk/kern/task_policy.c)。这是本次调度修正的依据，不是对所有历史失败的根因证明。

## 实现

- **E02 媒体交接：**UDP socket、加密包和解码 PCM 就绪时唤醒工作线程；appsink 回调只发通知，不读样本或等待应用。耗尽单轮预算后用 1 ms 期限继续处理，保留收包处理上限；源生成的短时追赶也保留至少 1 ms 间隔，避免突发塞满编码队列。
- **E03 调度：**仅独立 Rust/GStreamer 媒体线程采用 `SCHED_OTHER`、基础优先级 47，读回实际策略。仍为可抢占的普通分时线程，未启用 Mach 时间约束。guard 不可跨线程移动，离开时恢复原策略和基础优先级。显式 pthread 调度会退出 QoS 模型，因此不用于 UI/Dispatch 线程池。
- **诊断：**分阶段记录墙钟与同次 CPU 时间；等待另记请求时长、最大额外等待和固定 8 条异常环。统计保留在非实时线程，不往设备回调加入系统调用或日志。媒体原有认证、撤销、80 ms 源期限、70 ms 目标水位、所有队列容量保持原值。
- **长测工具：**固定被测制品，检查实际数字读回；额外要求 loopback 丢包、迟到与 PLC 均为零。采集 Hub 与两路 Sender 的 CPU、RSS、physical footprint、线程及文件描述符，CPU 按单个逻辑核 100% 归一化。

## 验证

macOS workspace 格式、Clippy `-D warnings`、74 项常规测试与 Hub release 构建通过；新增回归检查 socket/native 通知唤醒及普通线程策略恢复。测试中的 ignored 用例不计为已运行。[检查结果](evidence/e02-e04/stability-result.json)、[测试日志](evidence/e02-e04/stability-tests.log)。

[控制与数字读回](evidence/e02-e04/stability-control-20260930.json)通过单/双路、增益/Mute/多 Solo、总控、权限/冲突/幂等、撤销与重启；[11 组实际故障](evidence/e02-e04/stability-completion-20260930.json)通过拥塞降级/恢复、慢控制、WSS 重订阅、真实落盘失败、44.1 kHz 原 UID 重开、单流故障隔离和被堵住的诊断输出；[真实采集隔离](evidence/e02-e04/stability-capture-control-20260930.json)通过 BlackHole 采集期间 6 秒慢控制，采集错误/丢帧为零。

[30 分钟结果](evidence/e02-e04/stability-soak-1800s-20260930.json)通过：BlackHole 实际读回 **86,400,000 帧**，静音帧为 0；Mixer 欠载、原生错误/回调超预算、丢包、迟到、PLC、PCM 缺口和队列丢弃均为 0。两路最大额外等待分别为 **1.148/1.141 ms**，源积压为 0；水位范围分别为 3142–3728 和 3219–3816 帧。RTP 序号跨过两次自然回绕，时间戳步长错误为 0。输出回调最大耗时 0.551 ms，小于 256 帧的 5.333 ms 周期。

本轮源为 CLI 的 437/659 Hz 测试音，经真实 UDP/DTLS-SRTP/Opus 和原生 Hub 输出进入 BlackHole，再由独立原生采集进程数字读回。真实 BlackHole 输入 Sender 另由上述采集隔离探针验证；不把测试音源描述为 30 分钟普通应用捕获。未加入受控负载、采样器或编译，保留通常的宿主活动。

数据取启动一分钟之后的采样。线程固定，描述符随控制连接回收后保持有界，内存未见持续增长；这些是本次 30 分钟观察，不外推为 24 小时保证。采集正常退出，Hub/两路 Sender 随后停止，临时凭证删除，设备采样率恢复。

CPU 计数的量纲在本轮采样期间发现并修正：`proc_pid_rusage` 给出 Mach ticks，按本机 `125/3` 换算为 ns，与 50 ms 进程 CPU 钟对照误差约 0.10%。音频、内存和描述符判据不受此修正影响；原始计数保留为该运行目录的 `result.raw-cpu-ticks.json`/`samples.raw-cpu-ticks.jsonl`，报告包含明确的换算记录。[量纲验证](evidence/e02-e04/stability-resource-clock.json)。

## 边界与复现

本轮只覆盖单台 macOS 上的真实 UDP/DTLS-SRTP/Opus、双 Sender、原生输出和 BlackHole 数字读回。没有进行 Windows/Linux 测试；跨机实体测量、8/24 小时矩阵与模拟端延迟没有据此验收。E05 自动发现/首次配对产品流程、E07 桌面 Mixer 和 E09 分发仍在各自工作包。

```sh
tools/dev cargo build --release --locked -p neonmix-hub -p neonmix-audio
tools/dev python3 tools/hub_soak_probe.py --device coreaudio:BlackHole2ch_UID --seconds 1800
```

所有依赖、临时身份、编译及测试产物均在项目内；探针结束清除临时凭证并恢复 BlackHole 采样率。失败的历史记录保留，不用新结果覆盖。
