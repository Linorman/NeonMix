# NeonMix Windows WaveRT render prototype

Scope: one fixed Windows 11 24H2 x64 render endpoint, hardware ID `ROOT\NeonMixAudio`, service `NeonMixAudio`, display name `NeonMix`. The internal endpoint names `WaveSpeaker` / `TopologySpeaker` remain stable across room name, IP and Sender changes. The source derives from Microsoft's simplified SysVAD `audio/simpleaudiosample`, pinned by `provenance.json`, under MS-PL.

The endpoint declares **48 kHz stereo PCM16 only**. Windows' shared-mode audio engine converts application formats; Rust's existing WASAPI loopback captures the selected render endpoint and converts PCM to the shared 48 kHz float32 protocol. No dedicated kernel/user PCM transport is introduced. Browser/music/game/system-sound, loopback timing, endpoint volume and lifecycle behavior remain Windows runtime gates.

The WaveRT synthetic clock advances from `KeQueryPerformanceCounter` and notification timers. It has no connection to Sender, Hub, TLS or Opus. Rendering consumes its bounded DMA timeline and produces no physical speaker output. DMA allocations are capped at 256 KiB, notification count at two, and active system render pin instances at one (the Windows audio engine mixes applications into that pin). Missing/inactive application behavior is determined by the shared audio engine and must be measured, not inferred from source.

The derivative removes the microphone endpoint, sine generator, PCM file writer and registry switches that could enable them. It publishes no hardware volume or mute node: the endpoint has no hardware amplifier and Windows must supply software endpoint volume. Rust does not multiply a second endpoint gain. This choice follows Microsoft's [software volume support](https://learn.microsoft.com/en-us/windows-hardware/drivers/audio/software-volume-control-support); actual loopback volume behavior still requires Windows measurements.

Notification registration/removal shares the timer's spin lock; teardown cancels and waits for the timer before releasing callback-owned objects. Allocation failures release reserved adapter ownership; invalid RUN transitions without a DMA ring are rejected. Format declarations, range negotiation and DRM bookkeeping remain based on PortCls. The package does not declare the sample's unverified DRM signature attributes or attempt protected-content bypass.

`tools/windows_driver_header_check.py` compiles the ten translation units on macOS against locked WDK/SDK 10.0.26100.6584 and links an unsigned x64 PE native image with WDF 1.33 import libraries. Its temporary Clang overlay repeats the `int` type already used by the WDF request-enum forward declaration; the native Windows build uses the original WDF headers. COFF/PE compilation is **not** proof of Windows loading, HVCI, HLK, Driver Verifier, signing or audio operation.

The native `NeonMixAudio.vcxproj` / `tools/build_windows_driver.ps1` path uses an installed Visual Studio C++/WDK integration read-only and project-local SDK packages. Outputs, PDB and logs stay under project `target/` and `artifacts/`. Signing is off in this source/build prototype; E09 must provide an appropriately signed catalog/package and idempotent root-device installation/update/uninstall. No installation or change to system security is performed by these scripts.

On 2026-10-01, GitHub Actions Windows Server 2022 / VS 2022 x64 MSBuild compiled and linked all ten translation units against the unmodified locked WDK headers, and passed native INF verification and Inf2Cat signability checks. The unsigned SYS/INF/CAT/PDB and resolved toolchain properties are archived. SHA256 and x64 native PE/NX/ASLR/CFG were independently checked after download. This establishes native build/package coverage only; none of the kernel-loading or audio-runtime gates above are implied.

The package also publishes a fixed EP\0 product-owner property (`{1A50C7B0-B766-4E50-9DF8-3F49B6583BD1},2`, string `com.neonmix.audio.virtual-output`). Rust accepts only eRender endpoints carrying this marker for the NeonMix provider; it does not identify devices by an editable friendly name. `output sync-name` writes PKEY_Device_FriendlyName through the standard property store and verifies readback, using administrative access only for this explicit action. Ordinary Sender operation remains read-only and does not elevate. The marker is a product-selection check, not a cryptographic trust boundary. Metadata propagation and naming require native Windows validation.
